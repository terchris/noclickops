## Design principle

**The Azure engineer owns the target-repo layout.** Repo layout, per-env variable names, pipeline names, container-app naming, RG naming, subscription assignment — all of that is set by the Azure engineer (via `copier-add-service` and Azure DevOps). noclickops's job is to **discover what exists** and **trigger / call** it. We:

- Do NOT clone `copier-add-service` to read the canonical schema — the schema is whatever's deployed in the wild.
- Do NOT invent naming conventions — we query Azure DevOps to find what's actually there.
- Do NOT modify the target repo's structure — `add-service`, `deploy`, etc. trigger pipelines; we never bypass them.
- Accept overrides (`--subscription`, `--resource-group`, `--app-name`, `--pipeline-name`) for values that can't be discovered.
- Degrade gracefully — `info` prints "not discoverable; pass `--<flag>` to override" rather than guessing.

This is the existing "wrap, never replicate" rule applied to layout: we wrap whatever the upstream pipeline definitions encode; we don't replicate authority over them.

## The target layout (v2)

```text
<repo>/
  .pipelines/
    add-service.yaml        # add-service pipeline definition
  services/
    <svc>/
      Dockerfile
      app/                  # service source code
      config.test.yaml      # per-env config — LIVES WITH THE SERVICE
      config.prod.yaml
      README.md
      .pipelines/
        service.yaml         # BUILD pipeline (docker build, trivy scan, publish artifact)
        deploy_service.yaml  # DEPLOY pipeline (consumes artifact, packages config, hands off downstream)
```

Generated by `copier-add-service`. The Azure engineer owns the template; noclickops consumes the result.

## Discovered facts (2026-05-29 — `az` queries against the test repo)

### Pipeline naming (confirmed)

`az pipelines list --repository <repo>` for `ABC100001-myservice` returned exactly:

| ID | Name |
|---|---|
| 1125 | `<repo>-add-service` |
| 1128 | `<repo>-<svc>-build` |
| 1129 | `<repo>-<svc>-deploy` |

Convention: every service has a `-build` + `-deploy` pair. `noclickops deploy <svc> <env>` triggers `<repo>-<svc>-deploy` (not `-build`). The deploy pipeline's `targetEnvironment` parameter selects test vs prod.

### Per-env config variables (confirmed)

Read from `services/postgrest/config.test.yaml`:

- `SERVICE_PORT`, `SERVICE_CPU`, `SERVICE_MEMORY`, `SERVICE_MIN_REPLICAS`, `SERVICE_MAX_REPLICAS`, `SERVICE_HEALTH_CHECK_PATH`, `SERVICE_HEALTH_PROBE_PORT`
- `ENABLE_PUBLIC_ENDPOINT`, `PERSISTENT_STORAGE`
- App-specific (varies per service): `OKTA_ISSUER`, `APP_BASE_URL` (postgrest-only).

`SERVICE_NAME` is set in the build pipeline YAML (`services/<svc>/.pipelines/service.yaml`), but it's identical to the folder name (`services/<svc>/` → `<svc>`) — noclickops derives it from the path, doesn't read the YAML.

### Subscription (discoverable via service connection)

ADO pipeline-level variables are empty for all three pipelines. Subscription is encoded in a service connection:

```text
$ az devops service-endpoint list --query "[?type=='azurerm'].{name:name, sub:authorization.parameters.scope}"
myteam-frontend-test-sp  /subscriptions/3aec5ff4-...-c36f2bf3ca2d
myteam-frontend-prod-sp  /subscriptions/<prod-id>
myteam-frontend-acr-sp   <ACR scope>
```

Convention: `<org-prefix>-<env>-sp`. noclickops parses `authorization.parameters.scope` to extract the subscription ID per env.

### Container-app name + resource group: not in this repo

`services/<svc>/.pipelines/deploy_service.yaml` does NOT run `az containerapp create/update`. It only:

1. Downloads the build's `deploy-package` artifact.
2. Appends `config.<env>.yaml` to a `metadata.env` file.
3. Republishes as `deployment-package-{env}` for a downstream system to consume.

The actual deploy — and therefore the container-app name and resource group — lives outside this repo, in a downstream system noclickops doesn't see.

**Backend-name hypothesis (empirical, not confirmed)**: `<svc>` (just the service folder name). Evidence: the Front Door routes `<svc>.example.cloud` → `<svc>` backend; a half-broken peer service (`v2service.example.cloud` returning HTTP 504) shows Front Door IS routing on `<svc>` even when the backend is unreachable, which only makes sense if the backend name matches `<svc>`. Resource group naming follows the platform convention (`rg-<something>-<region>`) — confirming requires Reader access on the test sub, which most developers don't have.

### Public-endpoint architecture

All `*.example.cloud` services in `FrontendPlatform` route through a single Azure Front Door per environment:

```text
<svc>.example.cloud
  → CNAME test-endpoint-frontend-<hash>.z02.azurefd.net      (Azure Front Door, one endpoint for the env)
  → CNAME mr-z02.tm-azurefd.net
  → <Front Door IP>
```

Cert is a Front Door-managed DigiCert / GeoTrust SAN cert with `CN=<svc>.example.cloud`.

**First-time deploy timing** ("firewall registration" the engineer flagged): adding a new custom domain to the Front Door + DNS validation + managed-cert provisioning takes ~30–60 minutes. Subsequent deploys (same domain, new image) are fast — Front Door routing + cert are already in place.

Implication for noclickops:
- The public URL is always `<svc>.example.cloud` for any service with `ENABLE_PUBLIC_ENDPOINT: "true"`. Discoverable without Azure access — just read `config.<env>.yaml` and apply the convention.
- For first-time public deploys, see PLAN-watch-live-deploy for the layered polling that handles the ~60 min wait.

## Per-command impact

| Command | v2 change |
|---|---|
| **`noclickops`** (lister) | None — layout-agnostic. |
| **`update`** | None. |
| **`status`** | None. `az pipelines runs list` is layout-agnostic. |
| **`create-pr`** | None. |
| **`merge-pr`** | None. |
| **`info`** | Reads `services/<svc>/config.<env>.yaml` (not `.pipelines/variables/<env>.yaml`). Renders the new field set. Live container-app section requires `--subscription` / `--resource-group` / `--app-name` overrides OR best-effort discovery via `az containerapp list` (which needs the user's own Reader access on the deployed subscription — the SP creds in the service connection are the pipeline's, not the human's). Degrades gracefully when access / overrides are missing. |
| **`deploy`** | Triggers `<repo>-<svc>-deploy` (was `-CD`). Builds happen via `<repo>-<svc>-build` separately — noclickops doesn't trigger the build directly; the deploy pipeline pulls the latest successful build artifact via its `resources.pipelines` declaration. |
| **`logs`** | Same RG/app-name gap as `info` live state. Gating (no degrade) — requires `--subscription` + `--resource-group` + `--app-name` overrides if discovery fails. |
| **`shell`** | Same as `logs`. |
| **`add-service`** | Triggers `<repo>-add-service` (unchanged). **BUT the new pipeline only publishes a `deployment-request` artifact in ~10–30s and exits** — the actual scaffolding (Copier + commit + PR) happens in a downstream system 1–2 minutes later. v1.5.x's pattern of "watch the trigger pipeline → find the PR immediately" never finds the PR. v2 needs to **poll for the PR by source branch (`add-service-<name>`)** after the trigger pipeline succeeds, with a generous timeout (~5 min). Then merge as before. |
| **`clean-sample`** | New sample shape (Express + minimal `app/`, no Next.js). Rewrite to detect+strip the new sample. |
| **`sync-lovable`** | Probably doesn't apply — the new layout's services have an `app/` folder with Express, not a Vite/React PWA root. Defer until there's a concrete Lovable-into-new-layout use case. |

## PLAN sequence

### PLAN-A — `lib/service.sh` rewrite for the new layout

Centralises the new layout's discovery logic:

- `read_service_config <svc> <env>` → reads `services/<svc>/config.<env>.yaml` into `parsed_*` globals.
- `discover_subscription <env>` → lists service connections, filters by `<prefix>-<env>-sp` pattern, parses ARM scope.
- `discover_deploy_pipeline <svc>` → `az pipelines list` + pattern-match `<repo>-<svc>-deploy`.
- `discover_containerapp <svc> [env]` → best-effort `az containerapp list -n <svc>` (the backend-name hypothesis); returns RG+name or empty if not found / no access. Accepts `--app-name <name>` override.
- `public_url_for <svc>` → returns `<svc>.example.cloud` if `ENABLE_PUBLIC_ENDPOINT: "true"` in `config.<env>.yaml`, else empty. Pure-derivation; no Azure call needed.

`info` / `deploy` / `logs` / `shell` all use these helpers — single source of truth for the new layout.

### PLAN-B — `info` rewrite

Uses `read_service_config` for the static section (port, CPU, memory, replicas, public-endpoint, persistent-storage, plus any app-specific vars present). Uses `discover_subscription` + `discover_containerapp` for the live section. Accepts `--subscription`, `--resource-group`, `--app-name` overrides. Degrades gracefully — static section always prints; live section either prints or labels "not discoverable; pass `--<flag>` to override".

### PLAN-C — `deploy` rewrite

Uses `discover_deploy_pipeline` to find `<repo>-<svc>-deploy`. Triggers via `az pipelines run` with `targetEnvironment=<env>`. `--watch` behaviour unchanged.

### PLAN-D — `logs` / `shell` rewrite

Same discovery layer as `info`'s live section. Both commands are gating (no graceful degrade) — fail with a clear "pass `--subscription <id> --resource-group <rg> --app-name <app>` to specify the target" message if discovery comes up empty.

### PLAN-E — `clean-sample` for the new sample shape

Detect the new sample (Express + `app/` shape) and strip it. The v1 Next.js-sample logic is dropped along with FRT support.

### PLAN-F — `add-service` async-PR polling

v1.5.x's `add-service` watches the trigger pipeline (succeeds in seconds) and immediately looks for the resulting PR (which doesn't yet exist — async downstream). v2 polls `az repos pr list --source-branch add-service-<name>` every 5s for up to 5 min after the trigger pipeline succeeds; merges when found. `--no-merge` stays as the fire-and-forget escape hatch.

### Version bump

v1.5.x → **v2.0.0** when PLAN-A through PLAN-F land. Semver major (target-repo contract change). v1 stays available via the `v1.5.x` tag for anyone still on FRT.

The `--watch-live` flag for first-time public-endpoint deploys is filed separately as [PLAN-watch-live-deploy.md](PLAN-watch-live-deploy.md) — ships as part of v2 or as a v2.1 follow-up depending on appetite.

## Risks

1. **Container-app naming convention unknown.** `discover_containerapp` will pattern-match by `<svc>`, but if the downstream system names containers differently (`<svc>-<env>`, `<repo>-<svc>`, suffix hashes, etc.), the heuristic misses. Always offer `--app-name` override; document it loudly.

2. **Subscription access mismatch.** The pipeline's identity (the service connection's SP) has Contributor on the deployed sub; the human developer may have nothing. `info` live section, `logs`, `shell` need the human's own access — failing closed with a clear message is the right behaviour. Don't try to use SP credentials from the service connection — that's a layer violation.

3. **Service-connection naming may not be org-wide.** The `<prefix>-<env>-sp` pattern was observed in FrontendPlatform. Other ADO projects in ExampleOrg might use a different convention. `discover_subscription` should fall back to "list all ARM service connections; if exactly one matches, pick it; if multiple, prompt or require `--subscription`".

4. **`copier-add-service` will evolve.** Each evolution may add / rename variables, change pipeline-name suffixes, restructure folders. Build noclickops around **discovery + overrides + graceful degrade**, not hardcoded names — so new variables show up in `info` automatically (or get ignored cleanly), and renamed pipelines surface via the same `az pipelines list` query.

5. **Downstream deploy system is opaque.** Whatever consumes `deployment-package-{env}` is the actual deployer — that's what determines RG and container-app names. If that system changes, noclickops's discovery may stop matching. Mitigation: keep the override path always working as the escape hatch.

## Out of scope

- **FRT layout support.** Dropped in v2. v1 users pin to `v1.5.x`.
- **GitHub-target support.** Future extension; not v2.
- **`sync-lovable` for the new layout.** Defer until a real use case exists.
- **Discovering the downstream deploy system.** Not noclickops's concern — overrides handle the gap.
